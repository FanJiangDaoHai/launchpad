# 功能开发标准操作流程（SOP）

> 开发一个功能从 0 到提交的完整步骤。

---

## Step 1: 读代码，找根因（5-15分钟）

**必须做的 3 件事**：
1. 读核心文件（涉及改动的类）
2. 搜索所有引用点（字段、方法、类型）
3. 画出"谁依赖谁"（一张简单的表即可）

**重点注意**：
- 区分"症状"和"病因"
- 不要听到需求就直接动手改
- 确认改动影响范围，评估能不能"只改一个文件"

---

## Step 2: 设计最小改动方案（5-10分钟）

**决策清单**：
- [ ] 只改核心文件，外围文件零改动或自动适配？
- [ ] API 保持兼容（加重载）还是明确断裂（批量替换）？
- [ ] 这个数据结构在热路径吗？
- [ ] 遍历顺序重要吗？

**重点注意**：
- 优先改底层数据结构，上层通过间接访问自动适配
- 如果必须改多个文件，列出完整的文件清单

---

## Step 3: 修改核心代码（按文件逐个来）

**顺序原则**：
```
数据层 → 管理层 → 查询层 → 测试 → 示例/文档
```

**每改完一个文件**：
1. 编译检查 `read_lints`
2. 修错误
3. 再改下一个

**重点注意**：
- 不要同时改 5 个文件最后一起编译
- 命名规范同步检查（`m_PascalCase`、PascalCase 方法/类）

---

## Step 4: 修改外围调用点

**场景**：API 签名变了，测试/示例/其他地方要跟着改。

**推荐做法**：
- 用 Python/Regex 脚本批量替换，不要手工改
- 替换后全局搜索确认没有遗漏

**重点注意**：
- 批量替换前先备份或确认 git 状态
- 替换完必须编译验证

---

## Step 5: 写测试

**必须覆盖**：
- [ ] 正常路径（基本功能）
- [ ] 边界路径（空、单元素、最大值、跨边界）
- [ ] 异常路径（非法输入、重复操作）
- [ ] 性能路径（高频操作、大量数据）

**重点注意**：
- 边界测试比正常测试更重要（bug 都在边界）
- 改了什么就测什么，不要测无关功能

---

## Step 6: 运行验证

**检查项**：
- [ ] 编译零错误零警告
- [ ] 测试全部通过
- [ ] 示例场景能跑通
- [ ] 没有异常堆栈

**重点注意**：
- 运行时异常优先看堆栈最底部（根因）
- 不要只看报错信息，要追溯调用链

---

## Step 7: Bug 修复（如果有）

**追溯流程**：
```
报错点 → 调用方 → 调用方的调用方 → ... → 根因
```

**常见根因类型**：
| 现象 | 可能根因 |
|------|---------|
| 空引用/越界 | 数据已删除但引用还在，或事件触发顺序错误 |
| 数据不一致 | A更新了但B没同步，缺少事件通知 |
| 性能骤降 | 热路径上做了不该做的事（遍历、分配、装箱） |
| 随机崩溃 | 多线程/事件重入/状态竞争 |

**重点注意**：
- 事件/回调触发前，数据必须处于合法状态
- 修完写个最小复现测试，防止回归

---

## Step 8: 性能优化（如果需要）

**决策顺序**：
1. 先定位具体瓶颈（Profile，不要猜）
2. 复杂度优化（O(n²) → O(n) → O(1)）
3. GC 优化（减少分配、对象池、预分配）
4. 缓存优化（空间换时间）

**数据结构选择**：
| 场景 | 选这个 | 不要选这个 |
|------|--------|-----------|
| 频繁 Add/Remove + 遍历 | `List` + 索引字段 + swap-back | `HashSet`（GC大） |
| 只查存在性 | `HashSet` | `List.Contains`（O(n)） |
| 需要顺序+索引 | `List` + `Dictionary` | 单独 `Dictionary` |

**重点注意**：
- Unity 中 GC 往往比 CPU 时间更致命
- 复杂度相同的情况下，选内存更紧凑的方案

---

## Step 9: 代码清理与规范检查

**检查清单**：
- [ ] 私有字段都是 `m_PascalCase`
- [ ] 没有公共字段（用属性）
- [ ] 没有遗留 `Debug.Log` / TODO / 死代码
- [ ] 公共 API 有 XML 注释
- [ ] 异常信息有意义

**重点注意**：
- 用搜索确认规范一致性，不要靠肉眼扫

---

## Step 10: 文档与记忆更新

**同步更新**：
1. **代码注释** — 公共 API 的 XML Doc
2. **README** — 如果 API 变了，示例代码要同步
3. **Daily Log** — `.workbuddy/memory/YYYY-MM-DD.md`
   - 改了什么
   - 为什么这样改
   - 踩了什么坑
4. **长期记忆** — `.workbuddy/memory/MEMORY.md`
   - 架构决策（如"实体容器用 List + ContextIndex"）
   - 用户偏好（如"偏好表格对比"）

**重点注意**：
- 写完功能再补文档，文档和内容保持一致
- 踩坑经验必须记录，下次遇到同样情况直接避坑

---

## 完整流程图

```
读代码找根因 → 设计最小改动 → 改核心(逐个文件+编译) → 改外围(批量替换) → 写测试 → 运行验证 → 修Bug(追溯根因) → 性能优化 → 规范检查 → 文档更新
```

**总时长参考**：
- 小功能（1-2个文件）：30-60 分钟
- 中功能（3-5个文件）：1-2 小时
- 大功能（架构改动）：2-4 小时
